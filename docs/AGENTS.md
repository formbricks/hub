# Repository Guidelines

## Project Structure & Module Organization
- `src/content/docs/`: Main documentation pages (`.md`/`.mdx`), including the landing page at `src/content/docs/index.mdx`.
- `src/content/docs/guides/`: Autogenerated sidebar section for guide content.
- `src/content.config.ts`: Starlight content collection/schema wiring.
- `astro.config.ts`: Site, sidebar, API reference, and plugin configuration.
- `public/`: Static assets served as-is (for example, `public/favicon.svg`).
- `src/assets/`: Project images imported in content/components.

## Build, Test, and Development Commands
- `pnpm install`: Install dependencies.
- `pnpm dev` (or `pnpm start`): Run local dev server at `http://localhost:4321`.
- `pnpm build`: Create a production build in `dist/`.
- `pnpm preview`: Serve the built site locally for validation.
- `pnpm format`: Run Prettier across the repository.
- `pnpm astro ...`: Run Astro CLI subcommands (example: `pnpm astro check`).

## Coding Style & Naming Conventions
- Use Prettier (`prettier --write .`) as the formatting source of truth.
- Prefer 2-space indentation and keep formatting consistent with existing files.
- Use `kebab-case` for doc filenames (example: `quickstart.mdx`).
- Keep docs frontmatter minimal and explicit (`title`, `description`).
- For TypeScript config/code, follow existing style: ES modules, double quotes, semicolons.

## Testing Guidelines
- There is currently no dedicated automated test suite in this repo.
- Minimum validation for changes:
  1. Run `pnpm build` to catch compile/content errors.
  2. Run `pnpm preview` and review changed pages manually.
  3. For formatting-sensitive changes, run `pnpm format`.

## Commit & Pull Request Guidelines
- Git history currently starts with a single concise commit (`initial commit`), so strict conventions are not yet established.
- Use short, imperative commit messages (example: `Add quickstart troubleshooting section`).
- Keep commits focused by concern (content, config, styling).
- PRs should include:
  1. A clear summary of what changed and why.
  2. Linked issue/context when applicable.
  3. Screenshots or short recordings for visible UI/docs layout changes.
  4. Confirmation that `pnpm build` succeeds.
